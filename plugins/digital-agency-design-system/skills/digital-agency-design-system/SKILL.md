# デジタル庁デザインシステム（DADS）：作る・審査する・直す

社内のメンバーが作るもの（社内文書・ツール・顧客向けの成果物）の**品質の下限をそろえる**ためのスキル。DADS に従わせる道具ではなく、誰が作っても下限を割らないようにする道具として使う。

このスキルは窓口。依頼を見て、作る・審査・直すの役に振り分ける。パスはこのスキルのフォルダ（`${CLAUDE_SKILL_DIR}`。以下 `SKILL_DIR`）からの相対パス。

このプラグインは個人による DADS のスキル化で、デジタル庁の公式配布物ではない。

## 1. 依頼の振り分け（最初に読む）

| 依頼の例 | 役 | 手順書 |
|---|---|---|
| 「画面を作って」「フォームを作って」「マニュアルを HTML で」「アーティファクトで」 | **作る** | `references/roles/build.md` |
| 「このページを審査して」「アクセシビリティを見て」「この URL を点検して」 | **審査** | `references/roles/review.md` |
| 「指摘を直して」「指摘3を直して」「直しておいて」 | **直す** | `references/roles/fix.md` |
| 「審査結果を報告書にして」 | 審査の記録から**報告書**（HTML）を作る | `references/roles/review.md` の「報告書にするとき」 |
| 「この資料（パワポ・.pptx）を確認して」「スライドを審査して」 | **審査**（PowerPoint） | `references/roles/office.md` |
| 「資料の指摘を直して」 | **直す**（PowerPoint） | `references/roles/office.md` |
| 「スライドで作って」「パワポで作って」「資料（PowerPoint）にして」 | 作るのはこのスキルの担当外 | slide-techvan に任せる（作り終えたら、このスキルで審査できると伝える） |
| 「このスキルを更新して」「最新にして」 | 上流の取り込み | 下の「8. 上流への追従」 |

**Claude Code・Cowork**（サブエージェントを呼べる環境）：
- 窓口は自分で作業しない。作る → `digital-agency-design-system:builder`、審査 → `digital-agency-design-system:reviewer`、直す → `digital-agency-design-system:fixer` に必ず任せる（役を分けるのは、作った本人が甘く採点するのを避けるため）。
- 作る役・直す役は、仕上げに自分で審査役を呼ぶ。審査役は直さない。
- サブエージェントの中から別のサブエージェントを呼べない環境では、作る役は審査の道具を自分で動かして軽い点検をする。直す役は直した分と修正前後のスクショをコミットして「再点検が必要」と返すので、窓口が審査役を呼んで深い審査をさせる。新しい指摘が出たら、もう一度直す役に任せる（重大度のルールどおり）。
- 直す役が「再点検が必要」と返したら、利用者に返事をする前に必ず審査役を呼んで再審査させる（Web も PowerPoint も同じ）。審査役の再審査を経ずに「直した」と報告しない。
- 再審査で新しい指摘が出ても、窓口は自分で直さない（直す役に渡す）。
- 審査役が「未点検（Chromium が無い）」と返したら、利用者に「審査に使うブラウザ（約 200MB）を入れてよいか」を聞く。了承を得たら「入れてよい」と添えて審査役を呼び直す。断られたら未点検のまま伝える。
- 直す役が「確認が必要なもの」を返したら、一覧で利用者に聞き、答えを添えて直す役を呼び直す。

**チャット（claude.ai。サブエージェントもブラウザも無い）**：
- Web は**作る**だけを、`references/roles/build.md` を読んで自分で行う。仕上げチェックはコード上で行う。
- PowerPoint の**審査・直し**は、ブラウザが要らないので、`references/roles/office.md` を読んで自分で行う（道具の Python の部品は `--install` で入れてよい。LibreOffice が無ければ、文字サイズとコントラストは未点検と伝える）。
- Web の**審査・直し**を頼まれたら、「実際に表示して点検する必要があるので、Cowork か Claude Code で頼んでください」と案内する。コードを読むだけの審査で代わりにしない。

**道具の場所**（Claude Code・Cowork。手順書に出てくるパスはここを使う）：
- 審査の道具：`${CLAUDE_SKILL_DIR}/scripts/audit/audit.sh`
- 審査の道具の依存（Playwright・axe-core）の置き場所：`--deps "${CLAUDE_PLUGIN_DATA}/audit"`（プラグインを更新しても残る）
- 1ファイルにまとめる道具：`${CLAUDE_SKILL_DIR}/scripts/bundle_html.py`
- PowerPoint の審査の道具：`${CLAUDE_SKILL_DIR}/scripts/office/pptx_audit.sh`（`--deps` は上と同じ）
- PowerPoint の直す道具：`${CLAUDE_SKILL_DIR}/scripts/office/pptx_fix.py`（`--pydir "${CLAUDE_PLUGIN_DATA}/audit/py"`）

## 2. 基準の優先順位

1. **顧客の基準**（ある場合）
2. **既存のテンプレート**（スライドマスタ、既存サイトの部品、ロゴの使い方など）。崩す変更は必ず事前に確認する
3. **DADS**（Web）／テクバン独自の Office 基準（スライドは `references/office-standard.md`。初版で岸のレビュー待ち。Word・PDF は今後追加）

顧客向けの成果物では、DADS は顧客の基準が決めていない部分（アクセシビリティなど）を補う「底上げ」として使う。

## 3. 守るもの

- プロジェクトの直下に `DADS-PROTECT.md` があれば、作業の前に読んで従う（書式と読み方は `references/protect-file.md`）。
- 無ければ、ロゴ・ブランド色・スライドマスタ・顧客の部品らしきものを見つけた時点で、直す前に一覧で確認する。

## 4. 重大度と印（DADS・基準）

| 重大度 | 決め方 |
|---|---|
| **致命的** | WCAG のレベル A の違反（例：入力欄にラベルがない、画像に代替テキストがない、キーボードで操作できない） |
| **重要** | WCAG のレベル AA の違反（例：コントラスト不足、375px で横スクロール、フォーカス表示が見えない、文字200%で切れる） |
| **軽微** | それ以外（AAA、axe の best-practice、文言の平易さ、見た目の細部） |

- DADS からの逸脱（トークン外の色、独自の部品、文字スタイルを使っていない、px 指定）には、重大度とは別に **DADS** の印を付ける。
- 自分たちで作ったページ（作る役の成果物）では、致命的・重要に加えて **DADS の印も 0 件**を合格の条件にする。他人や顧客のページでは、DADS の印は報告するだけ。
- 致命的・重要に DADS の印も付いたもの（例：DADS のフォーカス表示を消していて、フォーカスが見えない）は、重大度の扱い（確認せずに直す）を優先する。確認してから直すのは、DADS の印だけが付いた軽微なもの。
- PowerPoint では、DADS の印の代わりに、Office 基準（`references/office-standard.md`）だけに当たるものに **基準** の印を付ける（12pt 未満の文字、テーマ外の色・フォントなど）。扱いは DADS の印と同じ。
- 指摘は「平易な説明と直し方」を先に書き、WCAG の達成基準番号やトークン名は後ろに補足する。

## 5. 自動の軽い点検（作る・直すのたびに）

- 致命的な問題（と、自分で作ったページの DADS の印）は、渡す前に自分で直しておく。
- 重要な問題は上位3件だけ一言添える。
- 軽微な問題は黙っておく。「審査して」と頼まれたら全観点で深く点検する。

## 6. デザインのルール（共通）

**色**
- 定義済みトークン以外の色を使わない。Tailwind標準色（`blue-500` 等）や任意の16進コードは禁止。例外は `white` / `black`（と `DADS-PROTECT.md` のブランド色）。
- キーカラーは `key-*`（既定は青。`--color-key-*`）。主要ボタンは `key-900`、ホバーで `key-1000`。
- 本文テキストは `solid-gray-800`、見出しや強い文字は `solid-gray-900` が既存部品での使い方。補助テキストは白背景で `solid-gray-600`（5.7:1）以上の濃さにする。`solid-gray-536`（4.5:1）が文字に使える下限、`solid-gray-420`（3:1）は入力欄の枠線など非テキストの下限。
- 状態色はセマンティックトークンを使う：成功 `success-1/2`、エラー `error-1/2`、警告 `warning-yellow-1/2`・`warning-orange-1/2`。色だけで意味を伝えず、文言やアイコンも添える。
- 面の区切りは `solid-gray-50`（背景）や `solid-gray-420/536`（線）など、グレーの段階で表す。
- **ダークモードは作らない**。DADS にダークモードの色は無いので、背景は白で固定し、DADS に無い配色を作らない（アーティファクトなどでダークモード対応を求められても同じ。利用者が明示的に求めたときだけ確認する）。

**文字**
- フォントは Noto Sans JP（等幅は Noto Sans Mono）。HTMLでは Google Fonts で読み込む。
- 文字スタイルは名前で選ぶ：`{種類}-{サイズ}{太さ}-{行間}`。
  - 種類：`dsp`（大見出し）、`std`（標準。本文・見出し）、`dns`（詰めた表示。表やUI内）、`oln`（1行。ボタン・ラベル）、`mono`（等幅）
  - 太さ：`B`=700、`N`=400。行間：`170`=1.7倍。
  - 例：本文 `std-16N-170`、小見出し `std-20B-150`、ボタン文字 `oln-16B-100`。
  - Tailwindでは `text-std-16N-170`。素のCSSでは `dads-u-std-16N-170` クラス（global.css に定義）。
- 本文は16px以上を基本にする。文字サイズは rem で指定し、ブラウザの文字サイズ設定を尊重する。

**形・余白・影**
- 角丸：`4, 6, 8, 12, 16, 24, 32, full` のみ（Tailwind `rounded-8`、CSS `--border-radius-8`）。
- 影（エレベーション）：`1`〜`8`（Tailwind `shadow-2`、CSS `--elevation-2`）。多用しない。
- 余白・サイズは rem。素のCSSでは `calc(24 / 16 * 1rem)` のようにpx値を割って書くのが上流の流儀。
- ブレークポイントは 48rem（768px）、モバイルファースト。
- 余白のトークンは上流に無い。部品が無いページ全体の骨組みは、このスキルの推奨として次を使う（上流の規定ではない）：
  - `body`：背景 `white`、文字色 `solid-gray-800`、本文 `std-16N-170`
  - 本文の最大幅 `calc(960 / 16 * 1rem)` 前後、左右の余白はスマホ16px・48rem以上で24〜32px
  - フォーム項目どうしの間隔 24〜32px、セクション間 48〜64px、ボタンの並びの間隔 16px
  - 余白は 4 の倍数（Tailwindなら `gap-4`、`py-8` などの標準スケールで可。標準スケールの使用が禁止なのは色・文字・角丸・影だけ）

**操作とアクセシビリティ（WCAG 2.2 AA / JIS X 8341-3 が目標）**
- 正しいHTML要素を使う（遷移は `<a>`、操作は `<button>`、モーダルは `<dialog>`）。ARIAは最小限。
- フォーカス表示は「黒の4pxアウトライン＋黄色（`yellow-300`）のリング」。消さない・弱めない。global.css に入っている。
- ホバー表現は `@media (hover: hover)` の中に書く。
- `prefers-reduced-motion: reduce` でアニメーションを止める。`forced-colors: active` でも見えるようにする。
- タップ領域は44px以上を確保する（小さいボタンも上流は疑似要素で44pxにしている）。
- 画像には代替テキスト、フォームには必ずラベル（`form-control-label` 部品）とエラー文（`ErrorText`）。

## 7. 迷いやすい部品の選び方

部品の一覧は `references/generated/components.md`、トークンの一覧は `references/generated/tokens.md`。

- **タブ**：3タイプある。アプリ・管理画面・フォームは `<dads-tab-aria>`（矢印キー操作）、情報提供ページは `<dads-tab>`（Tabキー操作）、タブごとに別ページなら JSなしのリンクリスト（`basic-static.html`）。どのタイプでも、直前にタブ群の見出しを置き、タブリストに `aria-labelledby` でその見出しを結ぶ。
- **エラー文**：React版は `ErrorText` 部品。HTML版は部品ごとのクラス（`.dads-input-text__error-text`、`.dads-select__error-text`、`.dads-textarea__error-text`、グループ単位は `.dads-form-control-label__error-text`）を各部品の `errored.html` のとおりに使い、入力欄に `aria-invalid="true"` と `aria-describedby` を付ける。
- **必須／任意の表示**：`form-control-label` の印に `data-required="true"`（※必須）または `data-required="false"`（※任意）を必ず付ける。実例は必須側しか無いので任意側を書き忘れやすい。
- **表**：375px幅に収まらない表は `table/overflow-on-mobile.html` の `<dads-scroll-shadow>` で囲んで横スクロールさせる（ページ全体は横スクロールさせない）。
- **ページの見出し**：`h1` にも `.dads-heading` を使い、`data-size="36"`〜`"45"` 程度にする。見出し部品は上下の余白を持たないので、余白はページ側で付ける。

## 8. 上流への追従（保守する人向け）

利用者の手元には、プラグインの更新として届く（デスクトップアプリの「プラグイン」で更新する）。以下は、このスキルを管理するリポジトリ（`Kishi-Satoshi/digital-agency-design-system`）で作業するときの手順。

上流は `vYYYYMMDD` 形式のタグで頻繁に更新される。毎月1日に GitHub Actions が上流を確認し、更新があれば差分のプルリクエストを自動で作る（プラグインの version も自動で上げる）。マージすると、配布用リポジトリに自動で反映される。

手元で「スキルを更新して」「最新版にして」と頼まれたら：
1. `bash scripts/check_updates.sh` で取り込み済みの版（`VERSION.json`）と GitHub・npm の最新版を比べる。終了コード10が「更新あり」。表示される compare URL で差分を確認できる。
2. 更新があれば `bash scripts/update.sh` を実行する。4リポジトリを取得し、`assets/` と `references/generated/` と `VERSION.json` を作り直す（git・npm・python3 が必要。node があればTailwindテーマも再生成）。
3. `references/generated/components.md` の差分を見て、追加・削除・名前変更された部品と、このスキルの記述（色・文字・手順）に食い違いがないかを確認し、必要なら直す。
4. プラグインの `plugin.json` の `version` を上げる（上げないと利用者に届かない）。
5. 変更点（増えた部品、変わったトークン、破壊的変更）を短く報告し、ブランチにコミットしてプルリクエストにする（main に直接入れない）。

既に部品をコピーして使っているプロジェクトは自動では変わらない（上流も継続的なバージョンアップを想定していない）。必要な部品だけ、compare URL の差分を見て手で取り込む。
