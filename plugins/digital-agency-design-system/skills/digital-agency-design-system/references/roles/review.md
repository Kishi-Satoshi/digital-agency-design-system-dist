# 審査役の手順

手元の HTML・コード、または公開中の URL を、実際に表示して点検する。Claude Code・Cowork では `reviewer` エージェントがこの手順で動く。**審査役は自分では直さない**（ファイルを書き換えない。書くのは `.dads-review/` の記録だけ）。

PowerPoint（.pptx）の審査は `roles/office.md` の手順で行う（この文書は Web 画面・HTML 用）。

チャット（claude.ai）ではブラウザを動かせないので、Web の審査はしない。頼まれたら「Cowork か Claude Code で頼んでください」と案内する。

パスはこのスキルのフォルダ（以下 `SKILL_DIR`）からの相対パス。先に SKILL.md の「基準の優先順位」「守るもの」「重大度と DADS の印」「デザインのルール」を読んでおく。

## 観点

1. **アクセシビリティ**（JIS X 8341-3・WCAG 2.2 AA）
2. **DADS 準拠**（トークン・文字スタイル・部品の使い方）
3. **表示とレスポンシブ**（375px・1280px、文字200%）
4. **文言**（下の「文言の観点」）

## モード

| モード | いつ | 道具で見ること |
|---|---|---|
| 軽い点検 | 作る役・直す役が渡す前に呼ぶ | axe-core、375px のはみ出し、トークン外の色（`--quick`。スクショなし） |
| 深い審査 | 「審査して」「点検して」「アクセシビリティを見て」と頼まれたとき | 上に加えて、375px・1280px のスクショ、文字200%、Tab のフォーカス順、JS エラー |

## 対象と、表示のしかた

- **ローカルの HTML ファイル**：そのまま道具に渡す。
- **公開 URL**：一般公開のページならどこでもよい。読み取り専用（入力・フォーム送信・ログイン・購入はしない。道具が GET 以外の通信を止める）。指定されたページだけを見る（サイト全体を巡回しない）。
- **手元のファイル・開発サーバー**：エラー表示などの状態を確かめるために、入力や送信を試してよい。ただし外への通信は道具と同じく止め、スクショは記録の置き場所に置く。

審査のために作る一時ファイル（取得したページのソース、自作の確認用スクリプトなど）は、記録の置き場所か一時フォルダに置く。**対象のプロジェクトにファイルを置かない。**
- **React などの開発サーバー**：審査役は自分では何も起動しない。動いている URL を受け取る（作る役・直す役が起動して渡す。利用者からの依頼なら URL を聞く）。

## 手順

1. **守るものを確かめる**：対象のプロジェクト直下に `DADS-PROTECT.md` があれば読む。書かれたものは、指摘しても「守るもの」と明記する。
2. **記録の置き場所を決める**：対象のプロジェクトの `.dads-review/<YYYYMMDD-HHMMSS>-<対象名>/`（対象名はファイル名かドメイン。例：`20261022-160512-request`、`20261022-160512-www.techvan.co.jp`）。公開 URL の審査では、いまの作業フォルダの下に同じ形で置く。複数の審査が同時に動いてもぶつからないよう、必ず対象名を入れる。日時は `date +%Y%m%d-%H%M%S` で実際の時刻を取る。既に記録がある置き場所には道具が書かずに止まる（終了コード 2）。軽い点検は一時フォルダ（`--out` を付けない）。
3. **道具を動かす**（`scripts/audit/audit.sh`）：
   ```sh
   bash scripts/audit/audit.sh <URL かファイル> --out <記録の置き場所> [--quick] --deps <依存の置き場所>
   ```
   - 依存の置き場所は SKILL.md の「道具の場所」のもの（プラグインでは `${CLAUDE_PLUGIN_DATA}/audit`。一時フォルダに入れない）。
   - 最初に `bash scripts/audit/audit.sh --env` を実行し、`disposable`（Cowork・Claude Code のクラウドなどの使い捨ての環境）なら最初から `--install` を付ける。`personal`（各自の PC）なら付けない。
   - 終了コード 3（Node・Playwright・Chromium が無い）：各自の PC では、入れてよいかを利用者に聞いてもらうため、「未点検。入れてよければ --install で点検できる（約 200MB）」と返して止まる。コードを読むだけの審査で代わりにしない。
   - 終了コード 4（ページを開けない）：URL・ファイルの場所を確かめて返す。
4. **道具の記録を読む**：`summary.md`（問題の候補）と、必要なら `result.json`。深い審査では PNG のスクショも開いて目で見る（崩れ、重なり、読みにくさ、375px での見え方）。
5. **コードを読む**（手元のファイルがあるとき）：道具で分からないことを確かめる（下の「道具では分からないこと」）。
6. **候補を確かめて指摘にする**：道具の候補は誤検知がありうる。スクショとコードで確かめ、本当に問題なものだけを指摘にする。重大度と DADS の印を付ける（SKILL.md の定義どおり）。
7. **記録を書く**（深い審査のとき）：`findings.md` を `audit.sh --findings <記録の置き場所>` に標準入力で渡して書き出す（審査役は Write を使わない）。書式は下のとおり。
8. **返す**：下の「返し方」。

## 道具では分からないこと（コードとスクショで見る）

**アクセシビリティ**
- 画像の代替テキストの中身が、画像の役割に合っているか（飾りなら `alt=""`）
- 見出しの構造が内容に合っているか（ページに `h1` が1つ、レベルが飛ばない）
- リンク・ボタンの名前だけで行き先や動作が分かるか（「こちら」「詳細」だけになっていないか）
- エラーの出し方：何が誤りかと直し方を文字で示し、`aria-invalid` と `aria-describedby` で入力欄に結び付けているか
- 色だけで情報を伝えていないか（必須、エラー、状態）
- 動き・自動で切り替わるもの：止められるか、`prefers-reduced-motion` で止まるか
- タップ領域が 44px 以上あるか（DADS の基準。WCAG 2.5.8 は 24px）

**DADS 準拠**（DADS の印を付ける）
- 部品のクラス名・`data-*` 属性・構造が上流の実例（`assets/html/components/<dir>/*.html`、React は `.tsx`）どおりか。似た見た目の独自部品を作っていないか
- 色・角丸・影がトークン由来か（生の色コード、Tailwind の標準色が混じっていないか）
- 文字が文字スタイル名（`std-16N-170` など）で指定され、単位が rem か
- フォームに `form-control-label` 部品を使い、必須／任意の印（`data-required`）があるか
- フォーカス表示（黒の4pxアウトライン＋黄色のリング）を消していないか
- 背景は白か（ダークモードの配色を作っていないか）

**表示**
- 375px・1280px のスクショで、重なり・切れ・読みにくい行の長さがないか
- 文字200%のスクショで、文字が重なったり読めなくなったりしていないか

## 文言の観点

| 観点 | 重大度 |
|---|---|
| リンク・ボタンの名前だけで行き先や動作が分かる（WCAG 2.4.4・2.4.6） | WCAG のレベルどおり（2.4.4 は A＝致命的、2.4.6 は AA＝重要） |
| エラー文が、何が誤りかと直し方を示している（WCAG 3.3.1・3.3.3） | 3.3.1 は A、3.3.3 は AA |
| ラベルと説明文が入力内容と合っている（WCAG 2.5.3・3.3.2） | A |
| 一文に一つのことを書いている。専門用語に説明がある。同じものを同じ言葉で呼んでいる（表記のゆれがない） | 軽微 |

## 重大度の付け方（SKILL.md の要約）

- WCAG のレベル A の違反＝**致命的**、AA の違反＝**重要**、それ以外（AAA、axe の best-practice、文言の平易さ、見た目の細部）＝**軽微**。
- DADS からの逸脱には、重大度とは別に **DADS** の印を付ける。
- 迷ったら、WCAG の達成基準番号を確かめてから決める。番号が付けられないものは軽微。

## findings.md の書式

```markdown
# 審査結果：<ページ名または URL>

- 対象：<URL またはファイル>
- 日時：<YYYY-MM-DD HH:MM>
- モード：深い審査
- 道具の記録：summary.md・result.json・スクショ（このフォルダ）
- まとめ：致命的 <n>／重要 <n>／軽微 <n>（うち DADS の印 <n>）

## 指摘

### 1. 【致命的】入力欄にラベルがない
- 場所：`input[name="name"]`（index.html 32 行目）
- 困ること：画面読み上げソフトの利用者には、何を入力する欄か分からない。
- 直し方：`form-control-label` 部品で囲み、`<label for="name">お名前</label>` を付ける。
- 補足：WCAG 4.1.2（レベル A）、1.3.1。DADS の部品 `form-control-label`。
- DADS の印：なし
- 守るもの：該当なし

### 2. 【重要】…

## 確認できたこと

- 道具で確かめたこと（axe-core、375px・1280px、文字200%、Tab のフォーカス順）
- 目で確かめたこと

## 確認できなかったこと

- 画面読み上げソフトでの実際の読まれ方、ログイン・送信の後の画面 など
```

指摘は「平易な説明と直し方」を先に書き、達成基準番号やトークン名は「補足」に回す。番号は 1 から振り、直す役と利用者が「指摘3」と呼べるようにする。

## 返し方

- **軽い点検**：致命的と DADS の印の指摘はすべて、重要は上位3件だけを、場所と直し方つきで返す。軽微は返さない。
- **深い審査**：利用者には、まとめ（件数）と、致命的・重要の指摘を番号順に返す。軽微は件数だけ伝え、詳しくは findings.md にあると書く。findings.md の場所も伝える。
- **未点検**のときは、その理由（Chromium が無い など）と、どうすれば点検できるかを返す。

## 報告書にするとき（「報告書にして」と頼まれたときだけ）

提出用の報告書を、DADS のデザインの単体 HTML で作る（作り方は `roles/build.md`。PowerPoint にはしない）。構成：

1. **概要**：対象、日時、目的
2. **評価サマリー**：致命的・重要・軽微・DADS の件数と、全体の所見（3行程度）
3. **指摘一覧**：findings.md の指摘を、平易な説明と直し方を先に、補足を後ろに
4. **点検範囲と方法**：見たページ、道具（Playwright・axe-core の版）、確認できたこと／できなかったこと

報告書には必ず「本書は事前点検であり、JIS X 8341-3 への適合を表明するものではない」と明記する。報告書は審査役ではなく、窓口（または作る役）が findings.md をもとに作る。
