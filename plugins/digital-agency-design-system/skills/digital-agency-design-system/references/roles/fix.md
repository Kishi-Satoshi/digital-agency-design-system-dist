# 直す役の手順

審査の指摘を直し、最後に審査役に再点検させる。PowerPoint（.pptx）の直しは `roles/office.md` の手順で行う（この文書は Web 画面・HTML 用）。Claude Code・Cowork では `fixer` エージェントがこの手順で動く。チャットでは Web の直しはしない（再点検で表示できないため）。頼まれたら「Cowork か Claude Code で頼んでください」と案内する。

パスはこのスキルのフォルダ（以下 `SKILL_DIR`）からの相対パス。先に SKILL.md の「守るもの」「重大度と DADS の印」「デザインのルール」と、`roles/build.md`（部品の使い方）を読んでおく。

## 受け取るもの

- 審査の記録 `.dads-review/<日時>-<対象名>/findings.md`（「指摘3を直して」と言われたら、その対象のいちばん新しい findings.md の番号）。無ければ、先に審査役に深い審査をさせる。
- 直す対象のファイル（findings.md の「場所」）。

## 直す順番

1. **WCAG の致命的・重要**：確認せずに直す（DADS の印が一緒に付いていても同じ）。
2. **DADS の印だけが付いたもの**（独自部品を DADS の部品に置き換える、トークン外の色をトークンに変える など）：直す内容の一覧を見せ、了承を得たものだけ直す。**ただし、作る役が今作ったばかりのページなら、確認せずに直す。**
3. **軽微**：一覧を見せ、了承を得たものだけ直す。

どの順番でも、次のものは**必ず確認してから**直す：
- `DADS-PROTECT.md` に書かれたファイル・色・部品・メモ
- 書かれていなくても、テンプレート由来らしいもの（ロゴ、ブランド色、スライドマスタ、顧客の部品、顧客のスタイルガイドに沿った部分）

確認は、まとめて一覧で行う（1件ずつ聞かない）。サブエージェントとして動いていて利用者に直接聞けないときは、確認が必要なものを直さずに一覧にして返し、窓口に聞いてもらう。

## 手順

1. **Git で管理されているかを確かめる**（`git rev-parse --is-inside-work-tree`）。
2. **Git 管理下のとき**：
   1. 作業中の変更が無いかを `git status` で確かめる。あれば、利用者に確かめてから進める（勝手にしまったり消したりしない）。
   2. 別ブランチを作る：`git switch -c dads-fix/<YYYYMMDD-HHMM>`。
   3. 指摘を直す。1 つの指摘を直すたびに、何を変えたかを控えておく。
   4. 下の「再点検」を行い、その記録を `.dads-review/<日時>-<対象名>-after/` に置く。
   5. 修正前後のスクショを比べられるように、修正前（審査のときの `.dads-review/<日時>-<対象名>/`）と修正後の PNG だけを `git add` する。`findings.md`・`result.json` などはコミットしない。
   6. コミットする。メッセージは「DADS の審査の指摘を直す（指摘 1, 2, 5）」のように、直した指摘番号を書く。
   7. **push と PR の作成は、利用者に確認してから**行う（外に出る操作のため）。`gh` が使えれば PR を作る。使えなければ、ブランチ名と PR の本文案を渡す。
   8. PR の本文：
      ```markdown
      ## 直した指摘
      | 番号 | 重大度 | 内容 | 直し方 |
      |---|---|---|---|
      | 1 | 致命的 | 入力欄にラベルがない | form-control-label で囲んだ |

      ## 修正前後（375px）
      | 修正前 | 修正後 |
      |---|---|
      | ![修正前](.dads-review/<日時>-<対象名>/narrow-375.png) | ![修正後](.dads-review/<日時>-<対象名>-after/narrow-375.png) |

      ## 直さなかった指摘
      - 指摘 4（DADS）：確認待ち

      ## マージ前に
      - [ ] `.dads-review/` のスクショを残すか消すかを決める（消す場合はマージ前にコミットで削除する）
      ```
      画像のパスは、GitHub で表示できるようにブランチ上のパスで書く。
3. **Git 管理外のとき**：元のファイルは変えない。`<名前>.dads-fixed.html` のように別名でコピーして、そちらを直す。下の「再点検」の記録も同じように取り、差分の要約と修正前後のスクショの場所を伝える。上書きするかは利用者が決める。
4. **再点検**（Git 管理下では 2-4 で行う）：審査役（`reviewer`）を呼び、直したページを深い審査で点検させる。審査役を呼べないとき（`Agent` ツールが無い環境）は、自分で再点検の判定をしない。修正後のスクショだけは自分で道具を動かして取る（`audit.sh <対象> --out .dads-review/<日時>-<対象名>-after --deps <依存の置き場所>`。合否の判定には使わない）。修正前後の PNG と直した分をコミットし、「再点検が必要」と、直したファイルを返して、窓口に審査役を呼んでもらう。PR の本文案もこのとき作る。新しく増えた致命的・重要があれば直し、もう一度点検する（2回まで。それでも残るものは残っていると伝える）。

## 返し方

- 直した指摘の番号と内容、直さなかった指摘とその理由（確認待ち、守るもの など）。
- 再点検の結果（致命的・重要・DADS の印の残り件数）。
- ブランチ名・コミット、または `.dads-fixed.html` の場所。
- 確認が必要なものの一覧（あれば）。
